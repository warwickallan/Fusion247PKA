# asdair/outcome — the regulars writer (the learning path)

The **only** writer for `asdair.regulars`.

`README.md` in this folder names this the **highest-value remaining gap**:

> `asdair.regulars` has no governed writer, so the commonest learning of all — "this list name means that
> product", i.e. a new `aka` alias — cannot be persisted through this path. Until that exists, alias coverage
> improves only by hand, and a fresh instance re-asks the same questions.

Confirmed against the live database before this was built: **no role holds INSERT or UPDATE on
`asdair.regulars`** — not `asdair_rw`, not `cp_worker`, not `cp_directus`. Only SELECT exists anywhere. So
aliases, harvested ASDA product ids and genuinely-new items could not persist at all. This module is that
missing writer.

It lives here, not in `services/asdair/skill/`, for the same reason every other writer does: that folder is
**read-only by contract** and its queries run inside `BEGIN TRANSACTION READ ONLY`. Nothing here weakens that —
`loadRegulars()` keeps reading exactly as before.

| Module | What it is |
|---|---|
| `buildRegularsUpdate.js` | **Pure.** Validates an operation and builds the row / SET payload. No DB, network, fs, clock or randomness — it `require`s nothing at all. Also owns `mergeAka` and `applyAkaMerge`. |
| `updateRegulars.js` | Writes one operation in a single transaction. The only place an INSERT or UPDATE against `asdair.regulars` is issued. |
| `update-regulars.js` | **The runtime caller.** `node --env-file=<env> update-regulars.js --file regulars.json [--dry-run]`. Validates everything before opening a connection; `--dry-run` writes nothing and connects to nothing. |

## Two operations, and no third

**`upsertRegular`** — create a genuinely-new regular (SOP-021 step 6: "an item found missing from the regulars
catalogue becomes a `regulars` row, not a note").

**Safe to re-run.** Before creating anything it asks whether this household already has a regular by that
**normalised** name — trimmed, whitespace-collapsed, lower-cased, the same normalisation `skill/planner.js`
`normaliseTerm()` matches with — and if so **adopts the existing row and changes nothing**, reporting its id.

The table's own `UNIQUE (household_id, source, name)` is not enough on its own: it is an exact, *source-scoped*
match, so it would happily accept `"Arla 4pt  Milk"` beside `"arla 4pt milk"`, or the same item again under a
different `source`. That is not cosmetic. `planner.js` treats **two active regulars answering one term as
AMBIGUOUS** and sends the line to a human — so a duplicate *breaks resolution for that item, every week*. The
unique constraint remains as the race backstop (`ON CONFLICT … DO NOTHING`, never `DO UPDATE`).

**`enrichRegular`** — update an existing regular by id, on a **strict column allowlist**:

```
asda_product_id, asda_url, aka, brand, substitutes_allowed, typical_qty, updated_at
```

Anything else is refused, by name, with the reason.

### Why an allowlist and not a denylist

A denylist is only as good as the last person who remembered to extend it; a column added tomorrow would be
silently writable. Here the SET clause is **generated by iterating the allowlist**, not filtered against it, so a
column that is not on the list has no path into the SQL at all. `updateRegulars.test.js` proves this the hard
way: it bypasses the pure builder and hands the SQL builder a payload stuffed with `active`, `name`,
`household_id`, `source`, `created_at` and a made-up column, then asserts none of them reach the statement and
none of their values become bound parameters.

### The three things this path can never do

1. **Never DELETE.** There is no delete operation, no `DELETE`/`TRUNCATE`/`DROP` text anywhere in the three
   files, and a test asserts that on the source.
2. **Never set `active = false` as a side effect.** `active` is not on the allowlist. Retiring a regular is a
   deliberate human act, not something a shop's learning does while recording a URL. (`upsertRegular` surfaces
   `existing_active` when it adopts a retired row — it never reactivates it.)
3. **Never touch `name` or `household_id` on an existing row.** They are the row's identity: the planner matches
   on `name`, and `household_id` is the boundary that stops one household's preferences reaching another's
   basket. If the household calls it something else, that is an **alias**.

## `aka` merges, it never clobbers

`asdair.regulars.aka` is `text[] not null default '{}'::text[]`. It is the accumulated memory of every way the
household has ever written an item down, so replacing it would destroy prior learning — the precise failure this
module exists to end.

- A caller **may not pass `aka`**. That is refused. The only way to change aliases is `add_aka`, which can only
  ever add.
- The merged array **always begins with the existing entries, in their existing order**. This is structural: they
  are pushed first and nothing removes them, so the result is always a superset of what was stored.
- De-duplication is **case-insensitive**, matching how the read path compares.
- Aliases are stored **normalised** (trimmed, whitespace-collapsed, lower-cased) so the stored form *is* the
  compared form, and `"Arla 4pt"` and `"arla  4pt"` cannot accumulate as two aliases for one thing.
- `NULL` and `[]` are both "no aliases yet".
- An item is never stored as an alias of itself — though an existing such entry is never removed either. This
  module does not edit history.

The new value is built from the array **read inside the transaction**, never from caller input. The UPDATE then
carries `AND aka = $expected::text[]`: if another writer added an alias between the read and the write, zero rows
match and the whole thing rolls back with a clear message rather than silently discarding somebody else's alias.

That guard is deliberately **not** `SELECT … FOR UPDATE` — in Postgres that requires the UPDATE privilege on the
row, and this role's UPDATE grant is column-scoped to the allowlist on purpose.

## `updated_at`

Allowlisted, but **never a caller value**: the writer always sets it to the SQL literal `now()`, the same
discipline `recordShopOutcome` uses to pin `checked_out`. A supplied `updated_at` is refused — back-dating the
record of when a row was last learned about is not something this path may do, and these modules have no clock.

## Credentials

`ASDAIR_WRITE_DB_URL` only (role `asdair_rw`), the same convention as every other writer here. Never hardcoded,
never printed, never logged. A test asserts no connection-string literal exists and that no other env var is read.

## Grants this path needs

**Not yet applied — Warwick/Larry apply these; the build never connects to the live database.** Least-privilege,
column-scoped:

```sql
GRANT SELECT (id, household_id, name, source, active, aka) ON asdair.regulars TO asdair_rw;
GRANT INSERT (household_id, high_level_category, category, name, brand, asda_product_id,
              asda_url, typical_qty, source, active, aka, substitutes_allowed)
  ON asdair.regulars TO asdair_rw;
GRANT UPDATE (asda_product_id, asda_url, aka, brand, substitutes_allowed, typical_qty, updated_at)
  ON asdair.regulars TO asdair_rw;
```

No DELETE. No TRUNCATE. No UPDATE on `name`, `household_id`, `active`, `source`, `id` or `created_at` — so the
three hard rules above are enforced **by the database as well as by the code**, and a bug in this module still
cannot retire, rename or remove a regular.
