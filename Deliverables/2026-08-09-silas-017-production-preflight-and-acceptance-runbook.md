## 1. THE KNOWN DIVERGENCE, stated honestly: proven on 17.4, landing on Supabase

I proved 017 on **PostgreSQL 17.4**, a single-purpose `initdb` cluster containing exactly
`public` + `asdair`, owned by the role that applied it, with two roles in the whole cluster.
The household database is a **Supabase** project. **These are not equivalent, and I will not
assume they are.** Six specific implications, each with the preflight that closes it:

### 1.1 Engine version is UNKNOWN and must be read, not assumed

Supabase projects run PG 15, 16 or 17 depending on provisioning date and whether the
project has been upgraded. My proof is 17.4; CI is `postgres:16`. Every feature 017 uses
(`generated by default as identity`, `jsonb`, partial unique index, `pg_constraint` lookup,
`btrim`/`length`, POSIX `~`, `add column … not null default` without rewrite) predates PG15,
and SQLSTATE `42710` is unchanged across all three. **The risk is low. It is still a reasoned
inference and not an executed one, and the version must be recorded before apply** (PRE-1)
so the record says what it actually landed on.

### 1.2 The schema population is 10× larger — this is what makes R1 real rather than theoretical

My cluster had two schemas. A Supabase project carries `auth`, `storage`, `realtime`,
`graphql`, `graphql_public`, `extensions`, `vault`, `pgsodium`, `supabase_migrations`,
`_realtime`, `cron`/`net` if enabled, plus `public` and `asdair`. **`pg_constraint` is
database-wide and constraint names are only unique per relation.** A constraint named
`shop_question_round_sane` on *any* table in *any* schema makes 017's guard return "already
exists" and **silently skip creating the real one** — and because the `do $$ … $$` block
raises nothing, the migration reports success. The three names are implausible collisions,
but the sweep is one query and the failure mode is silent. **PRE-2 is mandatory.**

**The same hazard applies to `create index if not exists`**, which matches on index *name*
within the schema. An index named `shop_decision_question_uniq` already existing on a
different `asdair` relation would skip the uniqueness that is 017's structural idempotency.
**PRE-6.**

### 1.3 Object ownership may differ from the applying role

`asdair` migrations `013`, `014`, `015` were **applied live and have no committed files**
(wayfinder plan `:335`). I cannot see what role applied them or what it did. 017 executes
`alter table asdair.shop_question add column …`, which **requires table ownership**, and
`grant … on asdair.shop_decision`, which requires ownership or `WITH GRANT OPTION`.
On my cluster the applying role owned everything by construction. **PRE-8** establishes it
here instead of assuming it.

### 1.4 Role inheritance can silently confer the privileges 017 relies on being absent

Supabase's role graph is dense (`postgres`, `anon`, `authenticated`, `service_role`,
`supabase_admin`, `authenticator`, `pg_read_all_data`, …). If `asdair_rw` is a member of any
role holding DELETE on `asdair.*`, R2 fails **without any grant naming `asdair_rw`**.
My cluster had no memberships at all. **PRE-5**, and every grant assertion below uses
`has_table_privilege()` rather than reading `relacl`, precisely because
`has_table_privilege()` resolves inheritance and `aclexplode` does not.

### 1.5 `ALTER DEFAULT PRIVILEGES` in the `asdair` schema would break insert-only at creation time

No committed migration sets default privileges (`grep "alter default" services/asdair/db/*.sql`
→ no match). **But 013–015 are uncommitted and were applied live.** If any of them ran
`alter default privileges in schema asdair grant all on tables to asdair_rw`, then
`create table asdair.shop_decision` would be born **with UPDATE and DELETE granted to
`asdair_rw`** — 017's own grant block would add nothing, no error would be raised, and the
entire immutability claim would be false on day one while every other check passed.
**This is the single most dangerous Supabase-specific divergence, and it is invisible unless
you look for it. PRE-3 is mandatory, and V4 catches it again after the fact.**

### 1.6 "Immutable" means immutable to the *application roles*, and Supabase widens who is outside that

The table owner always retains full privileges. On Supabase, the SQL editor, the MCP
connection and `service_role` all operate as `postgres` (or higher). So a `shop_decision` row
is immutable to `asdair_rw` and `asdair_ro` — the runtime — and **not** to anyone holding the
service key or dashboard access. That is the estate's established model (016) and correct for
this purpose, but the sentence "granted to NOBODY" in 017's header must be read as
"granted to no application role". **Not a defect; a reading instruction.**

**Also, for noise-suppression rather than action:** Supabase advisors will report
`shop_decision` as an RLS-disabled table. `asdair` is not a PostgREST-exposed schema and 017
grants nothing to `anon` or `authenticated`, so the table is unreachable by the anon key.
Per the HOBBY BRAIN rule this is **PARKED, not escalated** — recorded here only so the
advisor line is not mistaken for a defect introduced by 017.

### 1.7 One divergence that works in 017's FAVOUR

Finding **F3** (017 is not wrapped in `begin`/`commit`, so an interrupted `psql` run leaves it
partly applied) is a `psql` property. If the apply route is Supabase `apply_migration`, the
statements are submitted as one batch and are expected to be transactional — which would
discharge F3 on this route. **I have not executed that and will not claim it.** It is stated
as an expectation, and the stop conditions below assume the *worse* case: that a failure may
leave the migration partly applied. Because 017 is genuinely idempotent (proven), the
recovery from a partial apply is to fix the cause and **re-run the same file** — never to
hand-patch objects.

### PRE-2 — R1: constraint-name collision sweep (database-wide, unqualified, exactly as the guard matches)

```sql
select c.conname,
       n.nspname  as schema,
       t.relname  as table
from pg_constraint c
left join pg_class     t on t.oid = c.conrelid
left join pg_namespace n on n.oid = t.relnamespace

                    'shop_question_round_parent_agree',
                    'shop_question_not_own_parent');
```

**Expect: 0 rows.** ⛔ **STOP on any row.** A pre-existing name means 017's guard will skip a
constraint that never gets created, and the migration will report success while the invariant
is absent. Do not apply. Re-plan the constraint name.

### PRE-3 — §1.5: default ACLs in the `asdair` schema

```sql
select n.nspname                       as schema,
       d.defaclobjtype                 as objtype,
       pg_get_userbyid(d.defaclrole)   as set_by,
       a.grantee::regrole::text        as grantee,
       a.privilege_type
from pg_default_acl d
join pg_namespace n on n.oid = d.defaclnamespace
cross join lateral aclexplode(d.defaclacl) a
where n.nspname = 'asdair'
order by 4, 5;
```

**Expect: 0 rows.** ⛔ **STOP on any row granting `UPDATE`, `DELETE`, `TRUNCATE` or `ALL` on
tables to `asdair_rw` or `asdair_ro`.** The new table would inherit them at creation and
insert-only would be false from the first row. Rows granting only `SELECT`/`INSERT` are
harmless — record them and continue.

### PRE-4 — R2: the upstream DELETE assumption, resolved through inheritance

```sql
select has_table_privilege('asdair_rw', 'asdair.shop_question', 'DELETE') as rw_delete_question,
       has_table_privilege('asdair_rw', 'asdair.shop_line',     'DELETE') as rw_delete_line,
       has_table_privilege('asdair_rw', 'asdair.shop',          'DELETE') as rw_delete_shop,
       has_table_privilege('asdair_rw', 'asdair.regulars',      'DELETE') as rw_delete_regulars,
       has_table_privilege('asdair_ro', 'asdair.shop_question', 'DELETE') as ro_delete_question,
       has_table_privilege('asdair_ro', 'asdair.shop_line',     'DELETE') as ro_delete_line,
       has_table_privilege('asdair_ro', 'asdair.shop',          'DELETE') as ro_delete_shop;
```

**Expect: all seven `false`.** ⛔ **STOP on any `true` for `shop_question`, `shop_line` or
`shop`.** A `true` means the FK referential actions give `asdair_rw` a route to mutate or
delete a `shop_decision` row it holds no privilege on — 017's immutability claim would be
**false on this database**, and the honest response is to say so to Warwick before applying,
not after. (`regulars` is informational: its FK is `NO ACTION`, so a DELETE there cannot
reach a decision — it is refused instead. Record it; it is not a stop.)

**This is the query I need run that I could not run myself.** It is the one preflight that
converts a residual into a discharged fact.

### PRE-7 — the FK targets are the shape 017 expects

```sql
select c.relname, a.attname, format_type(a.atttypid, a.atttypmod) as type, a.attnotnull
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
join pg_attribute a on a.attrelid = c.oid and a.attnum > 0 and not a.attisdropped
where n.nspname = 'asdair'
  and (   (c.relname = 'shop_question' and a.attname in ('id','shop_id'))
       or (c.relname = 'shop_line'     and a.attname = 'id')
       or (c.relname = 'regulars'      and a.attname = 'id'))
```

**Expect:** `shop_question.id` and `shop_question.shop_id` both `bigint`, both `NOT NULL`;

### PRE-8 — §1.3: ownership

```sql
select c.relname, pg_get_userbyid(c.relowner) as owner
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'asdair'
  and c.relname in ('shop_question','shop_line','shop','regulars')
union all
select 'SCHEMA asdair', pg_get_userbyid(n.nspowner)
from pg_namespace n where n.nspname = 'asdair';
```

**Expect:** all owned by the same role, and that role is the one the apply route connects as
(or a role the connecting role is a member of). ⛔ **STOP if `shop_question` is owned by a role
the applying identity does not hold** — `alter table … add column` will fail
`42501 must be owner of table`, and it will fail **after** nothing has been created, which is
a clean failure but a wasted authority window.

### PRE-9 — no data-dependent failure (assertion, not a query)

`add column question_round integer not null default 1` on a populated table is a metadata-only
operation from PG11 onward; every existing `shop_question` row acquires `question_round = 1`
and `parent_question_id = NULL`, which satisfies `..._round_sane` (1 ≥ 1),
`..._round_parent_agree` (NULL parent **iff** round 1) and `..._not_own_parent` (NULL parent)
**by construction**. There is therefore **no backfill and no possible constraint violation from
existing rows** — the deliberate no-backfill stance in 017's header ("a missing `shop_decision`
row means *decided before this table existed* or *not yet decided*; it NEVER means *no decision
was made*") is preserved. **No query needed; recorded so nobody invents one.**

### 3.4 ⛔ APPLY-TIME STOP CONDITIONS

| Seen | Meaning | Action |
|---|---|---|
| `42710 constraint … already exists` | A guard failed to guard — PRE-2 was skipped or a collision appeared between preflight and apply | **STOP.** Do not re-run. Run V-ALL to determine what landed, then report to Warwick. |
| `42501 must be owner of relation shop_question` | PRE-8 was skipped or ownership differs | **STOP.** Nothing was created. Resolve ownership, then restart from PRE-1. |

**The general rule: on any stop condition, do not re-run and do not hand-patch. Read the state

`has_table_privilege` across `asdair_rw` and `asdair_ro` on `shop_question`, `shop_line`, `shop`, `regulars`:

### PRE-3 — `pg_default_acl` on schema `asdair`. **PASS, with a note. This was the one that could have failed silently.**

**Expected 0 rows. Found 1.** Inspected rather than assumed:

```
granted_by: postgres   obj_type: r (table)   acl: {asdair_ro=r/postgres}
```

**It grants `SELECT` to `asdair_ro` and nothing else, to nobody else.**

**The dangerous case does NOT exist.** Silas's warning was that if a default ACL granted `ALL` to `asdair_rw`, then `create table asdair.shop_decision` would be **born with UPDATE and DELETE**, 017's grant block would add nothing, **no error would be raised**, and insert-only would be false on day one while every other verification passed. **That is not what is there.**

**The note, recorded because it is a real interaction:** `shop_decision` will be created **already carrying `asdair_ro` SELECT** from this default ACL. 017's own grant of SELECT to `asdair_ro` is therefore a harmless no-op rather than the thing establishing that privilege. It changes nothing about the insert-only claim — **no default ACL grants anything to `asdair_rw`** — but a future reader comparing 017's grant block against live privileges should know why `asdair_ro` already had SELECT.

**Both preflights pass. No collision, no drift, no partial application** — `shop_decision`, `question_round` and `parent_question_id` are all absent, and both roles exist. **Migration 017 is safe to apply on the evidence available.**
