## 2. Idempotency — PASS, and proven properly

Passes 2 and 3 both exited 0, emitting only `NOTICE ... already exists, skipping`.
But "didn't crash" is not idempotency, so a second database


**Three applications produce a schema byte-identical to one.** That is idempotency.

### A note on `shop_question_round_sane`

`round = 0` with a NULL parent is caught by `..._round_parent_agree` first, so a
naive test could conclude `..._round_sane` is dead. It is not — with a **non-null**
parent it is the only thing standing:

```
insert ... (question_round, parent_question_id) values (0, 1);
ERROR:  new row for relation "shop_question" violates check constraint "shop_question_round_sane"
insert ... (question_round, parent_question_id) values (-5, 1);
ERROR:  new row for relation "shop_question" violates check constraint "shop_question_round_sane"
```

Independently reachable and load-bearing.

## 5. Insert-only semantics are REAL — PASS

Executed **connected as `asdair_rw`**, the runtime role.

Grants as applied:

```
  grantee  | privilege_type
-----------+----------------
 asdair_ro | SELECT
 asdair_rw | INSERT
 asdair_rw | SELECT
```

```
### TEST 5.1 -- INSERT as asdair_rw : MUST SUCCEED
INSERT 0 1
### TEST 5.3 -- UPDATE as asdair_rw
ERROR:  42501: permission denied for table shop_decision
### TEST 5.4 -- DELETE as asdair_rw
ERROR:  42501: permission denied for table shop_decision
### TEST 5.5 -- TRUNCATE as asdair_rw
ERROR:  42501: permission denied for table shop_decision
### TEST 5.6 -- ON CONFLICT DO UPDATE as asdair_rw
ERROR:  42501: permission denied for table shop_decision
### TEST 5.7 -- INSERT ... ON CONFLICT DO NOTHING
INSERT 0 0
### TEST 5.8 -- the row is UNCHANGED
 id |  decision_kind  | decided_quantity
----+-----------------+------------------
  1 | quantity_change |                2
```

**The decision is immutable to the runtime role, by grant, proven.** The
`ON CONFLICT DO UPDATE` refusal is worth singling out: an upsert is the obvious
way a future author would "fix" a decision, and Postgres refuses it because
`DO UPDATE` requires the UPDATE privilege. The writer's actual shape
(`DO NOTHING`) works and writes nothing on conflict.

Also confirmed: `asdair_rw` holds `USAGE` on `asdair.shop_decision_id_seq`, so
inserts work; no column-level grants were added beyond the table-level ones.

## 6. `fakePg` vs Postgres — five divergences, all in the harness

`fakePg` models 3 of the 15 CHECKs, the composite FK and the unique index.
**The other twelve are covered in practice by `buildDecision()`**, which
validates all fifteen before any SQL is emitted. I probed for a shape the JS
accepts and Postgres refuses and **found none**: `optionalText` trims (so
whitespace-only names become NULL and are rejected earlier), JS `.length`
counts UTF-16 units and is therefore never *looser* than Postgres `length()`,
and the fingerprint anchors agree — Postgres rejects trailing newline, embedded
newline and uppercase exactly as JS does.

**So no false-accept was found. The divergences that do exist are about returned
values, and they are real:**

| # | Aspect | `fakePg` | Real Postgres + `pg` | Risk |
|---|---|---|---|---|
| **D1** | `bigint` columns (`id`, `shop_id`, `question_id`, `decided_regular_id`, `evidence_shop_line_id`) | JS **number** (`1`) | JS **string** (`"1"`) | **Highest.** Any `===`, `Map` key, or arithmetic against a decision id passes in tests and fails live. `fakePg` internally uses `String(...)` comparisons — the fake is defensive where its own consumers may not be. |
| **D2** | `timestamptz` (`interpreted_at`, `created_at`) | ISO **string** `"2026-08-03T09:00:00.000Z"` | **`Date` object** | A consumer calling `.toISOString()` works live, throws on the fake; string comparison or `JSON.stringify` differ both ways. |
| **D3** | `jsonb` key order | insertion order preserved verbatim | **reordered by Postgres** — `{"model_return":…,"grounding":…}` came back `{"grounding":…,"model_return":…}` | Any deep-equal or hash over the round-tripped evidence is fake-only. Relevant because `grounding_fingerprint` exists precisely to avoid parsing this jsonb. |
| **D4** | `jsonb` normalisation generally | stores the JS object as given | duplicate keys collapsed, whitespace lost, numbers renormalised | Same class as D3. |
| **D5** | Returned column set/order | object spread order, and the fake row omitted nothing but ordered differently | `RETURNING` list order | Cosmetic unless a test asserts `Object.keys()`. |

**Executed side by side** — same spec, same `recordDecision`, two backends:

```
                          fakePg                real Postgres
id                        number   1            string   "29"
shop_id                   number   1            string   "1"
question_id               number   11           string   "11"
decided_regular_id        number   1            string   "1"
decided_quantity          number   3            number   3          <- integer, so agrees
interpreted_at            string   "2026-…Z"    Date(2026-08-09T14:05:45.788Z)
created_at                string   "2026-…Z"    Date(2026-08-09T14:05:45.788Z)
decision_evidence keys    model_return,grounding   grounding,model_return
```

Note `decided_quantity` is `integer`, not `bigint`, so it agrees — which makes
D1 **more** dangerous, not less: the returned row is a *mixed* bag of string ids
and numeric quantities, and that inconsistency is invisible in the fake.

**None of these is a defect in 017.** They are limits on what the existing green
test suite proves, and they belong to `fakePg`, not to the schema.

### F2 — an undocumented precondition of the immutability claim

017's header says UPDATE and DELETE are *"granted to NOBODY"*, and against
`asdair_rw` that is proven true. But **FK referential actions execute with the
table owner's authority and bypass grants entirely.** Demonstrated:

```
=== owner deletes the shop_line (ON DELETE SET NULL fires) ===
DELETE 1
 26 | existing_regular | evidence_shop_line_id -> (nulled)     <- a "no UPDATE to anybody" row was MUTATED

=== owner deletes shop_question 10 (ON DELETE CASCADE fires) ===
DELETE 1
(the decision row is GONE)                                     <- a "no DELETE to anybody" row was DELETED
```

So the decision's immutability rests on a **second, unstated condition**:
`asdair_rw` must not hold DELETE on `shop_question`, `shop_line` or `shop`.
Today it does not, and I proved it:

```
delete from asdair.shop_question where id = 2;  -> ERROR: permission denied for table shop_question
delete from asdair.shop_line     where id = 99; -> ERROR: permission denied for table shop_line
delete from asdair.shop          where id = 1;  -> ERROR: permission denied for table shop
```

`asdair_rw` holds only `INSERT, SELECT, UPDATE` on all three. **The claim holds.**

**Recommendation (documentation only, no code change):** 017's grants comment
should state that immutability depends on the absent DELETE grants *upstream*
too, so that a future migration adding `DELETE` to `asdair_rw` on
`shop_question` is recognised as silently un-doing 016/017's immutability model.
Note also that the table **owner** always retains full privileges — "immutable"
means immutable to the application roles, which is the estate's established
model (016) and correct for this purpose.

Separately, and consistent with the migration's own closing note:
`asdair.shop_decision` is absent from 012's enumerated grant matrix. Since 012
does not currently apply on a clean database at all (F1), these two want
resolving together whenever 012 is next touched.

### F3 — no transaction wrapper (observation, low consequence)

017 is not wrapped in `begin`/`commit`. Under `psql`, each statement autocommits,
so an interrupted run leaves the migration partly applied. Because the migration
is genuinely idempotent (proven above), re-running completes it. Recorded, not
raised.
