## Findings

1. **Two genuinely dirty trees**, both expected and neither touched by this ticket:
   - `C:/Fusion247PKA` (primary) — the six untracked Cairn intake files already known
     from this session's baseline `git status`; explicitly out of scope to touch.
   - `.../agent-af69ebb565829ee34` — a pre-existing baseline worktree with an
     uncommitted change. **Not investigated or modified per the estate's standing
     rule**: baseline worktrees are evidence, not cleanup permission, and disposition
     alone (not remediation) is this ticket's job.
2. **`unpushedCount` came back `null` (unknown) for most `agent-*` worktrees** — they
   have no configured upstream (`fatal: no upstream configured for branch ...`), which
   is expected for locally-created agent worktrees that were never pushed. Per the
   evaluator's own missing-field discipline (INV-1 spirit, carried into this ticket):
   `null`/unknown is reported as unknown, never coerced to `0` ("no unpushed commits").
3. **Live-worker matching is best-effort and has a known blind spot, called out rather
   than hidden**: F-7 in `02-MAP.md` is still open RESEARCH fog — this ticket does not
   claim to resolve it. The Windows process scan matches on process command-line text,
   which means a process whose command line happens to *embed* another worktree's path
   as literal text (for example, a diagnostic script passed via `node -e "..."` that
   contains the string `C:/Fusion247PKA-governor` in its own source) can self-match.
   That is exactly what happened in this capture: this reconciliation run itself was
   invoked via `node -e` with the governor path embedded in the script text, so its own
   process appears in *both* the primary checkout's and the governor worktree's live-pid
   lists. This is a real limitation of command-line-text matching, not a bug in the path
   boundary check (which was fixed — see next finding) — a durable fix needs a
   different signal (e.g. a session/task registry) and is left to F-7's own resolution,
   not silently patched over here.
4. **Bug found and fixed by running against the real estate, not by unit tests alone**:
   the first implementation matched live workers with a naive
   `commandLine.includes(path)`. Because `"C:/Fusion247PKA"` is a literal substring of
   `"C:/Fusion247PKA-governor"` (and `-audit`, `-tower`, `-w01`), the primary checkout
   was spuriously credited with every live worker actually running in those sibling
   worktrees. The synthetic unit tests written first did not catch this because they
   never paired a prefix-name with its own suffixed sibling. Fixed with a path-boundary
   check (`referencesPath` in `worktree-recon.mjs`) and a regression test added
   (`worktree-recon.test.mjs`, "a sibling worktree with a shared name prefix is never
   falsely matched"). Re-run against the live estate after the fix to confirm the
   correction actually changed the observed output, not just the test suite.

## Never-deletes guarantee

`worktree-recon.mjs` contains no `git worktree remove`, no `git branch -D`, no
`rmSync`/`unlinkSync`, no `rm -rf`, and no `--force` flag anywhere — enforced by an
automated source-scan test (`the module never invokes a destructive git or filesystem
operation`), not just a design intention.
