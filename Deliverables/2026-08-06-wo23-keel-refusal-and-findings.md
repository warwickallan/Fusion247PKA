## 🔴 F1 — HIGH. The stated root cause was WRONG, and this is the finding that matters

Larry's order asserted the stale cue survived because `return-cue-sweep.mjs` skips its cross-session
test when the `SessionStart` payload carries no `session_id`.

**Refuted by the code path.** `return-cue-consume.mjs` line 109 refuses any marker whose `session_id`
differs from the current session:

```js
if (marker.session_id !== sessionId) continue;
```

A marker from a *different* session can therefore **never** be consumed, whatever the sweep does.
The stale cue **was** consumed — therefore its `session_id` **equalled** this session's id.

**The real defect:** the cue survived on **TTL alone, across a context boundary that PRESERVES the
session id** (`/clear`, resume, or compaction) — not across a session-id change.

**Consequence for any repair:** hardening the `currentSessionId &&` guard is a genuine latent
weakness worth closing, but it is **not the cause**, and fixing only it would produce a green that
leaves the observed defect live. Any repair must be proven against a marker whose `session_id`
**matches** the consuming session.

## F2 — MEDIUM. A false claim in a header comment

`return-cue-consume.mjs` lines 6–7 claim: *"Atomic claim via rename to `.claimed` (Windows: rename
fails if target exists → mutex)."* Node's `fs.renameSync` on Windows **replaces** an existing
destination. The mutex does hold — but because the **source** vanishes and the loser gets `ENOENT`,
not for the stated reason. Behaviour safe; documented reason wrong.

## F3 — LOW. Dead filter that reads like the duplicate guard

`return-cue-consume.mjs` line 98: `!n.endsWith('.claimed.json')`. Claimed files are named
`<id>.json.claimed`, which already fails the preceding `.endsWith('.json')`. The clause a reader
would credit with preventing double-claim is doing nothing.

## F4 — To establish, not yet a defect. `agent_type: unknown`

`return-cue-write.mjs` lines 40–42 default to `'unknown'` when the payload omits `agent_type`;
`formatCue` then takes `_default`. So `unknown` is **expected-by-design** for a payload lacking the
field. Whether this host's `SubagentStop` actually carries `agent_type` is **unestablished** and
needs the live payload.

## F5 — Scope fact. "Installed" has two halves that behave differently

- A change to **`.claude/settings.json`** is **not loaded until the host restarts** ("written is not
  loaded", root `CLAUDE.md`). A *registration* change therefore cannot be proven live inside one dispatch.
- A change to a **hook script** takes effect on the **next invocation**, because each hook spawns a fresh `node`.

Any acceptance must separate these. Larry's A4 conflated them.

## F6 — A4 was close to tautological as written

For project-scoped hooks there is **no separate install location** — `$CLAUDE_PROJECT_DIR/.claude/`
**is** the installed location. With a clean worktree at the governance head, source-to-installed
alignment is true by construction. A4 must be restated as: *committed blob vs the bytes at
`$CLAUDE_PROJECT_DIR/.claude/hooks/*` at the moment the host invoked them*, with the
settings-registration half called out separately per F5.
