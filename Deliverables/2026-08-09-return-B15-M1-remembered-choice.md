### One design decision I made that the order did not settle — stated plainly

**A failure to READ or WRITE the memory is caught, reported, and never fails a
shop.** I applied this to the write immediately and, on measurement, corrected
the read to match. The reason is not the test suite:

> **Migration 018 is authored, not applied (AC1). `asdair.remembered_choice`
> will not exist on the first live run.** An uncaught read would fail *every
> shop in the estate* between this merging and Larry applying 018 — a shop that
> is otherwise entirely correct, because a household with no memory simply asks.

This is `applyRulebook`'s established precedent, not a new one: where the
enrichment cannot be consulted, no line changes, every affected line stays held
for a human, and the reason is recorded. **Caught is not swallowed** — the
failure travels in `remembered_refused` on the step's own return and through
`deps.log('remembered_choice_read_failed', …)`. **Only the I/O is inside the
`try`**; the pure resolution rule is outside it, so a defect in the rule is loud
everywhere. Mutation `silent` below proves that reporting is load-bearing.
